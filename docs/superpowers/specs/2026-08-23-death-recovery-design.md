# Death Recovery and Timeline Design

**Goal:** Make player death recover without replaying already spawned agents, while keeping the configured timeline and writing continuous death-wait log rows.

## Scope

This change covers the linked death behaviors in `Assets/Script/GameLogic/CombatMgr.cs`, `Assets/Script/UI/MainView.cs`, and `Assets/Script/Utils/SessionLogger.cs`. It also verifies the existing config speed path. The runtime config remains `Assets/cfg.csv`; it has been updated to the formal configuration shape with `Total Time` and `spawn_id`.

## Behavior

- Normal game time starts at zero for each level and advances during active play.
- When HP reaches zero, the game immediately destroys every non-player agent and preserves the scheduling cursor. It must not rewind `gameTime` or `lastAgentIndex`.
- If no config entry remains with `Total Time > gameTime` at death, the level ends as a failure immediately. A non-final level automatically starts the next level; the final level remains on the failure screen.
- Otherwise, death starts a fixed five-second recovery window. The game clock continues to advance during this window, but no agents are spawned.
- When the window ends, entries whose configured `Total Time` is at or before the current game time are considered missed and are never spawned. The next future entry becomes the next scheduling target.
- Multiple entries sharing one `Total Time` are spawned together. A scheduling update drains all due entries rather than creating only one row.
- Recovery resets HP to 100 and gold/points to zero. The first recovered agent entry observes those reset values.
- If no future entry remains when recovery ends, the level ends as a failure. A non-final level automatically starts the next level; the final level remains on the failure screen.

## State Ownership

`CombatMgr` owns gameplay state, the five-second recovery countdown, agent cleanup, and the authoritative game clock. `MainView` renders active play, death waiting, and terminal failure; it must not drive recovery by an independent timer. `isGameOver` remains reserved for terminal state and must not pause the recoverable death clock.

The existing ordered config list and `lastAgentIndex` remain the scheduling source of truth. `AgentConfig` stores `Total Time`, and normal scheduling and recovery comparisons use that value. The cursor only moves forward; recovery never scans backward by wave or resets to a prior wave boundary.

## Logging

- The fatal gameplay second keeps its queued death event and records HP as zero.
- Every complete second in the recovery window writes exactly one `death_wait` row with:
  - empty `spawn_id` and `agent_type`;
  - `avatar_hp=0`;
  - `avatar_gold` equal to the value at death;
  - `n_reward`, `n_threat`, `n_coactive_fat`, and `n_coactive_tall` all zero;
  - no agent presence and no distance.
- `second` continues increasing without gaps. Recovery rows must be emitted even though gameplay input and agent simulation are suspended.
- The first entry after recovery is an agent row with HP 100 and gold zero.
- A spawn ID is registered only once per level. Replayed or rewound entries are prohibited, so `duplicate_spawn_id` must not be generated by death recovery.

## Config Speed

`BaseConfig.InitAllLevel` reads the `Speed` column into `AgentConfig.speed`. `CombatMgr.CreateItem` passes that value to `MoveableEntity.SetTargetPos`, which sets `FollowComp` speed. No production speed change is required; verification must confirm the formal `cfg.csv` value reaches `FollowComp` unchanged.

## Approaches Considered

1. **Explicit death-wait state (selected):** centralizes time, scheduling, cleanup, and log emission in `CombatMgr`; keeps UI as presentation only. This avoids split-clock bugs.
2. **Minimal `isGameOver` special case:** smaller edit but leaves timer ownership split between UI and combat code, making second-boundary behavior fragile.
3. **Full absolute-time rescan:** robust but unnecessarily broad because the ordered cursor already models the configured sequence.

## Error and Boundary Handling

- Empty or missing level config keeps the existing configuration error behavior.
- Same-second config entries are processed as a group in one scheduling pass.
- Normal completion retains the existing rule that the level ends after all scheduled entries have spawned and all field agents have exited. Death may skip entries but must never make a level longer than the same level without death.
- Explicit exit and normal win flows remain unchanged. Terminal failure writes `level_end`, closes the active logger level, and then either starts the next level or displays final-level failure.

## Verification

Add deterministic behavior tests or the closest existing Unity test/smoke harness for:

1. death mid-wave clears agents, keeps the cursor forward, and never repeats a `spawn_id`;
2. game time advances through five death-wait seconds and resumes at the first future `Total Time`;
3. logger emits one continuous `death_wait` row per wait second with the specified fields;
4. no future config entry causes immediate terminal failure at death, and recovery-end exhaustion follows the same terminal path;
5. same-`Total Time` entries all spawn together;
6. configured speed reaches the movement component unchanged.
